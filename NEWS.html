Change Log

All notable changes to this package will be documented in this file. Two things about its shape are worth stating, because neither is the usual one.

Entries are dated rather than numbered, and that is still true now that there is a release. rplatypus 0.2.1 reached CRAN on 2026-11-04, so there are two ways to have this package and they are different: install.packages() gives the submitted version, and remotes::install_github("maju116/rplatypus") gives the default branch, which is where work lands between submissions. A heading here is the version in DESCRIPTION - the one the next submission will carry - and the dated entries under it are what a commit gives you before it is sent. The 0.1.1 at the bottom is the 2020 package this one replaced.

Every entry names the engine it needs. The computation lives in pyplatypus and this package pins one exact version of it. A feature lands in the engine, the engine is published to PyPI, and only then can this package reach it - so the pin moving is part of a change here, not housekeeping alongside it. The pin is what stops a release of this package breaking because the engine drifted underneath it.

2026-11-13 - Two tests reached the engine on a machine that has none

The engine it needs: 0.8.0a85, unchanged. Nothing about the package’s behaviour moves here: this is a test that was missing a guard, and the gate that should have found it.

0.3.0 was submitted to CRAN and came back from the incoming checks with 1 ERROR on r-devel-windows and OK on r-devel-linux. Two tests of save_class_volumes() called it and expected a refusal, on a machine with a Python and no pyplatypus, so what arrived was ModuleNotFoundError: No module named 'pyplatypus' where a message about class names was expected. Both refusals are the engine’s - save_class_volumes() checks reference and names in R and forwards the rest, and the per-class filenames and the channel count against the class names have lived in the engine since pyplatypus 0.8.0a29 - so both tests need the engine and neither carried the skip_if_no_volumes their neighbours do. They are the only two in the suite in that state, counted by running the whole of it with the engine made unreachable: FAIL 2 | SKIP 287 | PASS 1180 before, FAIL 0 | SKIP 289 | PASS 1180 after.

The reason nothing here caught it is the other half of this entry. The R-CMD-check jobs are commented “Deliberately without Python. This is how CRAN sees the package”, and nothing implemented that: a runner ships a Python and has a network, so reticulate::py_require() resolved the engine through uv the first moment a test touched the bridge. The submitted commit’s own Windows job downloaded cpython-3.13.18, torch (120.9MiB), torchvision and opencv-python-headless during checking tests and reported FAIL 0 | SKIP 313 | PASS 1047, against CRAN’s FAIL 2 | SKIP 313 | PASS 1045 - the same skip count and two passes fewer, because an unguarded test is not a skipped one and no skip count can see this. Those five jobs now set RETICULATE_PYTHON to a path that does not exist, which overrides py_require() entirely and removes the engine rather than merely declining to ask for it, and tests/testthat/test-cran-gate.R holds that line to the comment in both directions, so removing either one is loud. The engine job is unchanged and still exercises the bridge.

2026-11-11 (later) - This package now says which Python it needs

The engine it needs: 0.8.0a85, unchanged. This is about the interpreter the isolated environment is built on, which is R’s own question and not the engine’s.

maju116/rplatypus[#338](https://github.com/maju116/rplatypus/issues/338): reticulate::py_require() takes a python_version and this package passed none, so the Python of that environment was whatever uv’s candidate list offered first. Measured: that list begins 3.11.11, 3.10.16, 3.12.9, 3.9.21, 3.13.2 and is not sorted by version, so with no constraint the choice came off the head of a list this package had no opinion about.

It now asks for the engine’s own floor, >=3.11, and what that changes is the shape of the failure rather than the usual case. On this machine the answer is 3.11.11 either way - a no-op where it does not bite. Where it bites is a machine whose first candidate is below the floor: without the constraint uv builds an environment it then cannot resolve, and the user reads that no version of pyplatypus==0.8.0a85 matches, on a route where they never chose a Python at all. With it, reticulate stops first and names the constraint and the versions it found, in R, before anything is downloaded.

The floor is not a second opinion: tests/testthat/test-python-floor.R fetches the engine’s manifest and holds the two together, so a floor that moves there turns this package red until it follows - the pin’s ratchet one field over, and test-linter-pin.R’s shape because that is the same relationship about ruff.

Both escape hatches were measured rather than assumed. PLATYPUS_ENGINE_PATH resolves exactly as before, 3.11.11, and the warning that route prints was confirmed to predate this change by running the same probe without it. RETICULATE_PYTHON overrides py_require() entirely, so the constraint is recorded and has no effect there, and both of its startup messages still fire.

2026-11-11 - ?platypus_fit offered two devices where the engine takes any torch name

The engine it needs: 0.8.0a85, unchanged - this is R’s own prose about the engine’s table, and the engine has been right the whole time.

maju116/rplatypus[#336](https://github.com/maju116/rplatypus/issues/336): platypus_fit(device = ) was documented as "cuda", "cpu" or NULL, and the value is handed to torch as given - nothing in this package, the shipped shim or the engine checks it against a list. The engine’s own order of preference is three accelerators, cuda, mps and xpu, so "mps" was a value this argument has always taken and the help page did not mention.

The page is also the one place a reader would look for it. platypus_device() exists because of that backend - its own help page explains that a Mac reported cpu with a working mps backend in the same installation - so this package named mps where somebody diagnoses a problem and not where they ask for it.

The sentence now names "cuda", "mps", "cpu" and NULL, says the value is passed to torch rather than matched against a list, and offers "xpu" as forwarded rather than promised, because nothing in this project has run on one. The only claim it makes about mps is the one that was measured: an Apple M3 chose it and the same fit agreed with the processor on every figure the probe compared.

And the reason this was possible is the half worth having. device is an argument of the engine’s constructor rather than a specification field, so it is not one of the 117 names in the field-prose ledger - the one mechanism here that asks whether R’s prose still says the right thing. One function takes it, so the shared-@param census does not reach it either. It was unheld prose about a table in another language, and it has a receipt now: tests/testthat/test-device-param.R compares the devices the sentence offers against the engine’s own list, in both directions, through the running engine.

2026-11-10 - The pin moves to 0.8.0a85: an Apple machine was told its build was CPU-only

The engine it needs: 0.8.0a85, and this is a release whose whole value to an R user arrives through the pin moving.

maju116/pyplatypus[#468](https://github.com/maju116/rplatypus/issues/468): the engine answered cuda_build with "cpu-only build" whenever torch.version.cuda was falsy, which on a macOS wheel it always is - while that same wheel carries a working mps backend. platypus_device() forwards the engine’s device_report() verbatim, so an Apple Silicon user read three consecutive lines with the first denying the two under it:

torch      : 2.15.0
cuda build : cpu-only build      <- and the fit ran on the GPU
device     : mps
backend    : mps - not CUDA, so scores are not directly
             comparable with the published weights, which were trained on it

Measured on a borrowed Apple M3 Pro, macOS 26.7.2, torch 2.15.0, and it is the first time that path has executed anywhere: the machine this package is developed on is Linux with an NVIDIA card, and the macOS CI runner is a virtual machine whose graphics device has no Metal 2.0, so torch skips MPS there. The value answers about CUDA and about nothing else now - none where there is no CUDA build - because backend, device and gpu_present_but_unusable already carry everything the old string was reaching for.

One move for five releases. The pin sat at 0.8.0a80 on purpose: 0.8.0a81 is a pad colour this package does not expose, 0.8.0a82 is three sentences of that release’s own refusal, and 0.8.0a83 and 0.8.0a84 are prose and metadata whose R half was the sentence maju116/rplatypus[#327](https://github.com/maju116/rplatypus/issues/327) added. 0.8.0a85 is the first of the five an R user can feel, which is the ratchet working rather than a gap.

This package had written the impossible pair down as well. tests/testthat/test-bridge.R pinned cuda_build = "cpu-only build" beside backend = "mps" as its Apple Silicon fixture - a machine that cannot exist, since a macOS wheel has no CUDA and a working mps backend at once - and nothing in either suite compared the two, so it sat there as expected output while the printing method stayed indifferent to the value.

And the pin move produced a reading from the ledger of field prose that is new. All 117 engine digests held, so no description was rewritten; what moved was decode’s list of help topics, which gained evaluate_cases(). That list is read off this package’s own roxygen rather than the engine’s schema, so it went stale when evaluate_cases() gained the argument in maju116/rplatypus[#318](https://github.com/maju116/rplatypus/issues/318) the day before, the suite stayed green, and the regeneration a pin move triggers repaired it silently. The test holds a claimed topic to one that really documents the field and not the other direction - it says so in its own comment - so maju116/rplatypus[#333](https://github.com/maju116/rplatypus/issues/333) is that direction.

2026-11-09 (later still) - On macOS this needs Apple Silicon, and the sentence is held against the engine’s own page

maju116/rplatypus[#327](https://github.com/maju116/rplatypus/issues/327), which is maju116/pyplatypus[#459](https://github.com/maju116/rplatypus/issues/459)’s other half. torch has published no macOS x86_64 wheel since 2.2.2 - March 2024 - and the engine asks for at least 2.7, so on an Intel Mac there is no PyTorch it will accept. Found by a probe coming back from a real machine rather than by anybody reading.

R’s half is a different half, which is why it is prose rather than a refusal. The engine’s install fails on that platform; this package’s succeeds, because install.packages() is R and a CRAN binary and nothing here needs Python until something asks for it. So what an Intel Mac meets is a package that installs, loads, and then cannot make its first call. The README now says so in both places it already keeps facts of this kind - beside the ~5 GB CUDA wheel and the Pascal cap, which are the other two things about PyTorch rather than about this package.

And it is a second copy of somebody else’s fact, so it is held rather than written. test-platform-note.R fetches the engine’s README from its default branch, reads the torch version out of the engine’s own claim, and compares it with both of the copies on this page - test-brand.R’s shape, including the kind of positive control that section needs, because a network answering no for its own reasons is otherwise indistinguishable from a page that changed. The version is read out of each document by its role rather than compared as a formatted string.

What is deliberately NOT here is a refusal. Unlike the engine, this package has code running on that machine before uv does - Sys.info() answers Darwin and x86_64 - so it could refuse by name, which would be better than whatever reticulate says today. Two things have to be measured before that is written: where it may fire, since CRAN runs an x86_64 macOS flavour and a package that refuses to load there is a package that gets archived, and what it replaces, since nobody here has read the message it would improve on. [#327](https://github.com/maju116/rplatypus/issues/327) carries both, and it waits on a machine rather than on a decision.

And one sentence on that page was false, found while editing the section it is in. About the engine told a reader that uv cache clean pyplatypus is not enough to clear a stale index response and that the whole index directory had to go. It is enough, and this project’s own record has it enough on six engine releases - most recently 0.8.0a83, where both caches refused the version minutes after it was published, that command removed 271 files and 2.9 MiB, and the very next install succeeded with nothing else done. The heavy lever is still named, as the fallback it is.

The engine it needs: none beyond the pin, which stays at 0.8.0a80. The fact is the engine’s 0.8.0a83 README, and reading that page is what the new test does.

2026-11-09 (later again) - The CRAN gate is --as-cran minus one section, and a check that dies before its verdict now fails

maju116/rplatypus[#322](https://github.com/maju116/rplatypus/issues/322), which is this morning’s own entry corrected - and then the repair corrected by a measurement.

[#319](https://github.com/maju116/rplatypus/issues/319) stopped the workflow overriding check-r-package’s default args, so --as-cran reached R CMD check. The flag is only half of that gate: before calling rcmdcheck the action sets _R_CHECK_CRAN_INCOMING_ to the string false whenever it is empty, and R consults the flag for the CRAN incoming feasibility section only when that variable is unset. So the section never ran - and that is where the URL and DOI checks live, the maintainer line, Days since last update, and bad_version, an insufficient package version, which is the one WARNING-level item in there.

Turning it on was the obvious repair, it was tried, and it made the gate worse. The section needs CRAN’s own package database, and from a GitHub runner the fetch of PACKAGES.in timed out at 60 seconds: read.dcf could not open the connection, R CMD check printed Execution halted, and rcmdcheck reported success. Measured on one tarball, three ways, and in CI:

predict() answers per image and is joinable. type = "class" gives a row per image with key, label, predicted and probability; type = "probability" gives a matrix of images by classes with the keys as row names. Named rather than ordered, which is the lesson predict(space = "source") cost on the semantic side: a prediction handed back as a bare sequence has to be paired with whatever else the caller holds by position.

What is refused, by name, is as much of this as what is returned. space and the cases/each pair describe a grid and a split of masks too large to hold at once, and neither means anything for one label per image. evaluate(at = ) is refused for the same reason. evaluate_cases() is refused for a different one: a case here is one image whose score is 0 or 1, so a split’s worst case is 0 for any model that gets a single image wrong - a number that carries nothing while reading like one that does.

2026-10-26 - a detection epoch stops weighting batches alike (engine 0.8.0a42)

The numbers plot(fit) draws for a detection run change, and nothing you wrote changes with them.   • Semantic and instance runs are untouched. Their epoch was repaired in 0.8.0a40 and the arithmetic there was a different one.

It was measured before it was changed, on 150 instrumented epochs of the engine’s own BCCD example: both poolings pick the same epoch, and that is reported as too close to call rather than as no effect - the gap between them varies across the best epochs by 1.05 times the margin separating the winner from the runner-up. 2026-10-24 - a weight average fed per step (engine 0.8.0a37)

callback_ema() keeps an exponential moving average of the weights, updated after every optimiser step. That is what makes its decay mean what the literature means: 0.999 is 0.999 per step, so over 60 epochs of 200 batches it is 12,000 updates and a half-life of about 700 steps. A per-epoch version would have been the same name with values that do not transfer, which is why the engine gained a fourth callback hook rather than an approximation.

It is [callback_swa()]’s sibling and a run takes one of them: both replace the model when training ends, so the engine refuses the pair rather than applying them in whichever order the list happened to have. swa folds the tail uniformly from a declared start; ema weights recent steps more and needs no start at all.

Unlike swa it needs no pass over the training data afterwards. A uniform average of weights carries batch-normalisation statistics belonging to no epoch and has to have them recomputed; an exponential average of the buffers alongside the weights carries its own.

2026-10-24 - when a callback may act, and on what evidence (engine 0.8.0a34)

Three things that answer one question, which is why they arrive together rather than as three unrelated arguments.

callback_early_stopping() takes a warm-up: start as a fraction of the run or start_epoch as an epoch, one of the two and never both. patience could not express it, because it is in force for the whole run - a model needing fifteen epochs before its validation curve means anything forced patience > 15 permanently, paying that slack at the end where the point was to cut quickly. It delays the stopping and nothing else: an epoch inside the warm-up can still be the best one, and restore_best still returns to it.

callback_swa() takes start_epoch as the exclusive alternative to its fraction - the same concept, so the same two words.

callback_model_checkpoint() takes when, a named list of thresholds that must all hold before anything is written: list(val_dice = 0.9, val_loss = 0.2). The direction is derived, not configured - anything ending in loss has to be below its threshold and everything else above it, the rule monitor already uses - so there is no argument to get backwards. The names are checked against what the model reports when the specification is built. It is an extra gate beside save_best_only, not a replacement, and a run whose conditions never hold writes nothing and says so when it ends.

callback_stop_after(hours = ) is a wall-clock budget. An epoch cap cannot express it: how long an epoch takes is a property of the data and the shape. It is checked at the end of an epoch, so the real limit is the budget plus one epoch, and the run’s stop reason names the clock - a run that ran out of time does not read as one that converged.

Found by asking what a BraTS user would actually run, which is §4’s a feature is not shipped until something has used it the way a user reaches it applied to a refusal.

    Detected from the array rather than from the specification, which is the same test the engine applies in onehot_to_colours - so both halves refuse the same arrays, and a caller holding only a prediction can answer the question. A softmax prediction never trips it, since its channels sum to one and at most one can reach half; that control is a test rather than a sentence, because without it every ordinary run would start refusing.

  • save_class_volumes() is the same thing for volumes, and it is the case regions was built for. BraTS names three overlapping regions and stores them as volumes, so a writer that only handled pictures would have left the motivating dataset with a refusal and no route to disk. One NIfTI per class, each carrying the geometry of the scan it was predicted from - which is the whole reason this is not save_class_masks() with another extension.

    It needs no engine release: it goes through the same volume writer save_volumes() uses, so the affine, the integer labels and the grid check are those rather than a second copy. What is a second copy is the rule turning a class name into a filename, because the volume path never reaches the engine’s class_filename - so a test holds R’s rule to the engine’s over the names that are actually awkward, rather than a comment claiming they agree.

  • predict(type = "class") refused rather than computed when the classes overlap, and "class" is the default, so this is the first call an R user makes on such a fit. There is no one class per pixel to return: the channels are independent binary questions, they do not compete, and an argmax across them names one of the classes a pixel is in. The refusal says to ask for type = "probability" and names what writes it.

    Read off the specification the fit carries, which is a lever this package owns - the shape cannot answer it, because sigmoid channels and a softmax’s channels are the same array.

  • A single of value would have crossed over as a number rather than a list. reticulate turns a length-1 integer vector into a Python scalar, and the schema wants an array, so of = 4 had to be built with as.list(). Measured both ways before the code was written, and the engine refuses the scalar - so this would have been a refusal nobody could read rather than a silent wrong answer, on the most ordinary region there is.

    Still in [#152](https://github.com/maju116/rplatypus/issues/152), deliberately not here, and written as a paragraph rather than a heading because R CMD check reads every ### in this file as a version and says so: save_masks() refusing an overlapping prediction and the per-class writer that replaces it, inspect_masks() naming regions rather than numbering them, and the guide section. Each is independently worth having, which is why none waits for the others.
