Change Log

All notable changes to this package will be documented in this file. Two things about its shape are worth stating, because neither is the usual one.

There is no release yet. remotes::install_github("maju116/rplatypus") serves the default branch, so “the version I had working” is a commit rather than a tag. Entries are therefore dated rather than numbered: the heading they sit under is the version in DESCRIPTION, and the 0.1.1 below it is the 2020 package this one replaced.

Every entry names the engine it needs. The computation lives in pyplatypus and this package pins one exact version of it. A feature lands in the engine, the engine is published to PyPI, and only then can this package reach it - so the pin moving is part of a change here, not housekeeping alongside it. The pin is what stops a release of this package breaking because the engine drifted underneath it.

[0.3.0] - unreleased

2026-10-22 - what CRAN’s review of 0.2.0 asked for, forward-ported

0.2.1 answered the review on its own branch, from the commit the submitted tarball was built from, because sending main would have replied to two documentation comments with ten new exported functions. The same two fixes belong here as well, or 0.3.0 collects the same review.

Description writes 'PyTorch' and 'Python' in single quotes, as the policy asks of software names in Title and Description. R stays unquoted: the cookbook the review links does not address it, and its own Title Case example is Web Application Framework for R.

colormaps.Rd gained the \value tag it never had. It documents four exported objects rather than functions, so it carried \format alone; the tag is written in the roxygen source and states structure and meaning, not just class.

Worth keeping because it is a property of the review rather than of this release, and the first version of this paragraph understated it. R CMD check --as-cran with the manual, on R 4.5.3, does not flag a missing \value - checking Rd contents says OK with the tag absent - and neither does tools:::checkRdContents(). That was written as a fact about this machine. It is a fact about both sides: CRAN’s own automated pretest did not flag it either. Measured on the two logs, which are byte-comparable because the only difference between the submissions is this tag and two quoted names:

rplatypus 0.2.0, the version sent back    Windows 1 NOTE, Debian 1 NOTE
rplatypus 0.2.1, with the tag             Windows 1 NOTE, Debian 1 NOTE
mentions of `value` or `colormaps`        0 in all four logs

So the two submissions are indistinguishable to every check that runs, and the difference between them is exactly what the reviewer asked for. A clean pretest says nothing about whether the review will pass - a human read the .Rd files. The instrument that does ask the question is a check of our own: a page with \usage must have \value.

2026-10-22 - platypus_fact(), and a platypus fact when the package is attached

The pin does not move and the engine needs no release: this is the first thing in the package that has nothing to do with segmentation. The family is named after the animal, and platypus_fact() says something true about it. One fact is also printed when the package is attached in an interactive session; options(rplatypus.facts = FALSE), or PLATYPUS_FACTS=0 in ~/.Renviron, stops that.

Three things about it are deliberate, and each one is here because of what it prevents.

Choosing a fact does not touch the random number stream. sample() advances .Random.seed, so a fact picked at attach time changes what the user’s own set.seed(1) then produces - measured, runif(1) goes from 0.2655087 to 0.3721239 - and in a package offering seeded splits and deterministic = TRUE that is the worst available place for it. suppressPackageStartupMessages() is not a defence: the arguments are evaluated before the condition is signalled, so suppressing the message keeps the side effect and removes the evidence. The seed is saved and put back instead, and the test for it carries the naive implementation as its positive control.

Interactive sessions only, so a fact never lands in an R CMD check log, a CI run, a knitr render or anybody’s reverse-dependency check. And .onAttach rather than .onLoad, which is where this package’s other startup work lives: .onLoad also runs for rplatypus::fun(), which would print a platypus fact into the middle of a script that never called library().

Every fact carries the source it was read from, and the numbering is stable. Four of the twenty-five exist to correct a popular claim rather than to state one - the platypus does have a stomach, it does not grind food with gravel, “platypi” is not a plural and there is no accepted word for a baby platypus - which is the only form this could take in a package whose argument is that numbers should be measured rather than felt. A test holds every entry to having a source. The numbers are published the moment somebody quotes one, so facts are appended and never reordered, and a ledger of each fact’s opening in tests/testthat/test-facts.R fails if one moves.

tools/reference-groups.yml gains a group, The animal, last in the order. The matching line went into pyplatypus/tests/test_reference_groups.py at the same time: the shared order is an agreement about where a group goes rather than a list both sides fill, so the engine carries the title with no contents, as this package does for Records.

2026-10-16 - classes_from: one binary mask file per class

Needs pyplatypus 0.8.0a28, and the pin moves with this. maju116/rplatypus[#180](https://github.com/maju116/rplatypus/issues/180), whose engine half is maju116/pyplatypus[#91](https://github.com/maju116/rplatypus/issues/91) - an issue open since 2022, and this is the half the author’s decision of 2026-10-12 deferred rather than dropped.

Added

  • segmentation_data(classes_from = ), the fourth way of saying what a mask’s classes are and the only one that can express an overlap that was drawn independently: a vessel crossing an organ, or two annotators’ masks of the same structure. One pattern per class, in class order, matched against a sample’s mask files.

    It is regions’ sibling rather than its replacement, and the difference is the file on disk. regions derives overlapping channels from the values of one label map, which is how BraTS stores its ground truth; this reads channels that were separate files to begin with, because no single voxel value can hold two things drawn independently. Everything the two share is everything after the target: no background entry, a sigmoid per channel rather than one softmax across them, a voxel that may be in several classes at once, and a prediction save_masks() refuses - save_class_masks() and save_class_volumes() have written per-class files since 0.8.0a23 and needed nothing for this.

  • The exclusivity refusal is four-way, and that is the reason this is a code change rather than a pin bump. segmentation_data() enumerates its parameters, so the field would otherwise be an unused argument here; and a bare data list or a YAML file through platypus_spec() reaches the engine’s validator either way, so a constructor that refused what YAML accepts would leave the two R paths disagreeing about the same configuration. Measured on regions in rplatypus[#152](https://github.com/maju116/rplatypus/issues/152) and not re-guessed here.

  • The two pattern refusals say class where a class is what they are about - at least two patterns, and distinct ones. channels_from has the same two for images, and the engine answers both through one matcher with a noun; a copied message would have been the likely slip, so a test holds each to its own wording.

Fixed

  • A model that leaves separation to its weights is no longer read as semantic. 0.8.0a28 lets an instance model omit the field when weights names a file whose description records what it was trained to predict; this package reads a model’s task from that field, so a silent model was read as semantic and refused beside instance_data() as two tasks in one specification - which made the engine’s own headline example, written as an R snippet, impossible to write in R. A model now contributes the tasks it is admissible for and platypus_spec() intersects them with the data’s one task. rplatypus[#181](https://github.com/maju116/rplatypus/issues/181), and it is maju116/pyplatypus[#236](https://github.com/maju116/rplatypus/issues/236)’s R half, which that issue said did not exist.

    An intersection rather than a fallback, because a fallback swallows the case a wrong pairing is about: u_net() beside detection_data() says nothing about detection and is still refused. And a model that forgot separation and names no weights is still semantic and still refused beside instance data - the condition for being admissible is the engine’s own, weights being set, which is exactly where the engine permits the omission.

    Found by the field-prose ledger, which reported the engine’s separation description rewritten. Re-reading R’s @param against the new text is the only thing that step is for, and this time it turned up a mechanism rather than a sentence.

Documented

  • ?segmentation_data gains the field, and the configuration vignette gains a subsection under Overlapping classes instead of one per voxel rather than a section of its own - the section list is pinned by a test in each package’s suite. That subsection replaces the paragraph which said classes_from was deliberately not here, true of every release until this one.

2026-10-16 - the pin moves again, and a sentence on ?metrics was true of no release

Needs pyplatypus 0.8.0a27, and the pin moves with this. Nothing in this package gains a function: the engine fixed a defect in the release it shipped metric_surface_dice() in, and what this package owes is one corrected sentence and the test that would have caught it.

Fixed

  • ?metrics said a callback watching val_surface_dice on a tiled run “would wait forever”. It would not. Until pyplatypus 0.8.0a27 the engine accepted that pairing and the run stopped with an error at the end of the first epoch - the epoch paid for and nothing to show - because its specification layer decided which metrics a callback may watch from a list of names that surface_dice had never been added to, while its trainer decided what an epoch reports by asking the metric itself. One question, two answers, cldice in both and surface_dice in one. The engine now asks the metric in both places (pyplatypus[#239](https://github.com/maju116/rplatypus/issues/239)), so the pairing is refused when the configuration is read, which is what the page should have said and now does.

    A test holds it from this side, which is the part worth having: the claim is about a configuration this package sends, so it is this package’s to check rather than only the engine’s. It offers the engine both whole-mask metrics with a callback watching each, and carries two controls - untiled, the same callback is accepted, so the refusal is about the tiling; tiled with metric_dice(), it is accepted, so it is about the metric. Without both, a test like this passes on an engine that refuses the configuration for a reason of its own.

2026-10-16 - how far wrong the boundary is, and a loss that weights the rare class

Needs pyplatypus 0.8.0a26, and the pin moves with this.

Added

  • metric_surface_dice(tau = ), normalised surface Dice (Nikolov et al., 2018). The three overlap metrics ask how much of the mask coincides and metric_cldice() asks whether the structure does; none of them asks how far wrong the boundary is, which is the question a contour somebody has to approve is actually judged by. ?loss_boundary reports a model at Dice 0.9525 whose volumes run 5% small and 17% wrong per case, and no overlap column says that - a displaced boundary and a correct one of the same area score alike. It is also what loss_boundary() optimises, so until now that loss was being judged by the metric it exists to improve on.

    tau is required, because no default would be honest: a tolerance belongs to the structure and the dataset, and conventionally it is the inter-observer variability for what is being drawn. It is in millimetres where target_spacing puts the cases on a common grid and in voxels where it does not, which makes this the one metric here that reads the voxel spacing. Like clDice it is a property of a whole mask, so on a tiled run it is reported per case by evaluate_cases() and is absent from the epoch history.

    include_background is FALSE, and for a measured reason rather than the usual one: a background boundary is the foreground’s plus the edge of the picture, and that edge agrees between any two masks whatever happened inside them. On four random pairs at tau = 2 the background scored 0.6110 to 0.7030 against the foreground’s 0.5583 to 0.6266 - higher every time, which is agreement on the field of view.

  • loss_generalized_dice(), Dice with each class weighted by the inverse square of how much of the picture it occupies. The argument usually made for it is not the argument for it here, and the help page says so. It is introduced in the literature as a fix for Dice being dominated by the background; loss_dice() in this package is a mean over the class channels, so a 1% lesion already carries the same weight as the 99% around it. Measured on a 1% target, with one prediction finding the lesion and leaking an equal false positive and one missing it entirely:

    loss finds it misses it prefers finding by
    loss_dice() 0.1658 0.4731 0.3073
    loss_cce() 0.1600 0.1600 nothing at all
    loss_cce_dice() 0.1629 0.3166 0.1536
    loss_generalized_dice() 0.3278 0.9511 0.6233

    So it adds weight beyond an equal share - 1 to 9801 on that target - and the objective genuinely dominated is the per-pixel half of loss_cce_dice(). It is admissible as a model’s own loss at both segmentation tasks and as loss_boundary(region = ), which is the combination worth knowing about since both features are motivated by the same picture; separation_flows(loss = ) refuses it by name, because that target is a vector field.

Changed

  • ?loss_boundary said “the nine region losses” and there are ten. The count is gone rather than corrected: a number in prose with nothing holding it is the failure §3C exists to prevent, so the page states the rule - every loss except the three that score numbers and boundary itself - and a test holds that rule against the engine’s own union for BoundaryLoss.region. The same shape as the family page that twice failed to name a member of its family.

  • ?metrics describes the include_background split rather than one exception to it. It said the default differs “for clDice alone”, and the test holding that said the same in its own name; both would have gone on passing with a fifth metric in the package. The partition is asserted now - every metric is in one of the two groups, and a new one has to be put in a group before the suite passes.

  • The pin moves to 0.8.0a26, which also carries the measured answers to two things that were not built: cbDice, whose own gate now has a measurement pointing the other way, and the DIoU/CIoU/EIoU family. Both are answered on their issues rather than added as names.

2026-10-15 - the instance surface has a document that runs it

Needs pyplatypus 0.8.0a25, which is already the pin.

Added

  • vignette("instances"), the fifth worked document and the one the instance surface did not have. instance_data(), separation_rim(), the four decode_*, predict(decode = ), evaluate() with an average precision, overlay_instances(), overlay_instance_agreement() and instance_sizes() all shipped with tests and a configuration section, and nothing joined them end to end. §4’s entry is the argument: a feature is not shipped until something has used it the way a user reaches it.

    It is not a second Data Science Bowl vignette. The subject is the difference between the two readings of one dataset, so it opens with the published weights decoded two ways - 245 objects by nearest_seed against 180 by connected_components on the same picture, one forward pass, sixty-five touching nuclei run together - and puts dsbowl-unet’s mask beside the object map rather than describing it.

    Then it trains forty epochs beside the borrowed file in one specification, so evaluate() returns six rows and the comparison is a table rather than a paragraph. It ends where the measurement does: a count and a size distribution, in pixels, with the reason there are no micrometres - this dataset records no scale, and instance_sizes() takes a spacing precisely so that a document with one can say millilitres, as vignette("volumes") does.

    Two things in it were not planned and are the best of it. The borrowed weights reproduce the Hub card’s numbers exactly - 0.5445, 0.5390, 0.4822 - so the document controls itself. And the forty-epoch run lands about one run-to-run spread behind on foreground Dice while being four to five of them behind on average precision: the extra eighty epochs bought a sharper rim rather than a better mask, which foreground_dice cannot see because the rim is a third class whose quality only appears after decoding. That is a finding about time inside one recipe, and it sits beside rather than against the milestone’s finding about recipes. Both gaps are computed by the document, not typed into it, so re-knitting cannot leave them stale.

Fixed

  • Two vignettes were drawing into the same figure file, and one of them was this one. knitr names a figure after its chunk and every vignette here shares one fig.path, so an unprefixed history chunk wrote figures/history-1.png - which is vignette("data-science-bowl")’s training curve. Its picture became an instance model’s, silently: the file was still there and still a plot. Found by listing the built tarball, recovered with git checkout because the original was committed, and now held by a test that reads every shipped vignette and fails when two claim one path. The test demands no collision rather than a naming convention, because the first document to use a name breaks nothing.

2026-10-15 - a fourth set of published weights, and a score that needs its decoding

Needs pyplatypus 0.8.0a25, which is what the pin moves to here.

Added

  • weights = "dsbowl-instances" works, and it is the first published name whose score is not one number. A U-Net trained to tell touching nuclei apart on BBBC038v1 - interior, rim and background - measured on the same 134 held-out images dsbowl-unet reports:

    decoding instance AP objects found
    decode_nearest_seed() 0.5445 5,378 of 5,999
    decode_watershed() 0.5390 5,378 of 5,999
    decode_connected_components() 0.4822 4,914 of 5,999

    Foreground Dice 0.9118, the mask all three rows share.

    This side needed the pin and nothing else, which is the cheapest kind of change here and worth naming as its own shape: available_weights() reads the registry out of the engine, so the fourth name arrives in that data frame the moment the pin moves. No R code was written for it.

    What was written is the receipt. The description is what an R user reads before trusting a number, and 0.0623 separates the best row from the worst against a run-to-run spread of 0.009 - so a score quoted without its decoding is not a property of the weights. A test holds that description to its own arithmetic: every score in it has to name a decoding, the gap it claims for the separation signal has to be the gap between the rows it quotes, and the perfect-mask figure beside it has to be the larger of the two. Checked against the arithmetic rather than against the four decimals, because the measurements live in the Hub repository and nothing on this side can confirm 0.5445.

    The entry’s own claim is the instance milestone’s finding rather than a recommendation: the separation signal is worth +0.0623 here, a perfect semantic mask is worth +0.2398, and a perfect mask through connected components caps any model at 0.7655. The mask is the limit on this data. The weights are published so that the measurement can be argued with by somebody who did not take it.

Changed

  • The field-prose ledger records the new engine, and the diff is the reason this is a line rather than a silent regeneration: tests/testthat/fixtures/field-prose.yml moved its engine: line and not one of its 104 digests. No configuration field’s description changed in 0.8.0a25, so no @param on this side needed re-reading. Regenerating without looking at that diff is how the ledger would become a rubber stamp.

2026-10-15 - the two instance axes can be asked about

Needs pyplatypus 0.8.0a24, which is already the pin.

Added

  • available_separations() and available_decodings(), which completes the family. Eight of the ten listings the engine publishes were here and these two were not, so every axis of a specification could be asked about except the two that are only on the instance task - the newest ones, where a reader is least likely to know the names already.

    Found by comparing the two public surfaces name by name rather than by reading either, and it is the reference group’s own description that makes it a defect rather than a wish: the group these two sit in says it holds “the listings that ask the engine what those names are, rather than asking you to remember them”, with separations and decodings listed in it and no listing for either.

    Each carries the column it is opened for: needs on a decoding, the separation it requires - empty for connected_components, which is why that one is always available - and head_channels on a separation, how wide a head that target makes. Both come from the engine’s own rows rather than being named on this side, so a listing that grows a field arrives here with no R change; a test holds the other six listings to exactly three columns, because a bug in that would add a column everywhere rather than drop one here.

Changed

  • A test called “every decoding the engine offers has a constructor” now asks the engine. It compared a list written beside it, so the engine could have grown a fifth decoding with nothing failing - the same shape as the warning this morning, a declaration beside a mechanism that does not do it. There is one for separations now too.

2026-10-15 - the wrap past the end of the palette is reported

Needs pyplatypus 0.8.0a24.

Changed

  • overlay_instances() warns when a picture needs more colours than colours has. It names how many it needs, how many there are, and how many objects lost the guarantee.

    Both packages were silent here until now and the silence was a gap rather than a decision: the engine’s own colouring helper said in its docstring that overlay_instances reported it, and nothing in either package emitted anything. Filed from this side while [#154](https://github.com/maju116/rplatypus/issues/154) was being written, fixed in the engine as maju116/pyplatypus[#231](https://github.com/maju116/rplatypus/issues/231), and followed here the same day it was released - a warning on one side and silence on the other would be exactly the divergence [#154](https://github.com/maju116/rplatypus/issues/154) exists to prevent.

    The wrap is worth a word because it is the one case this figure answers its own question wrongly. Its subject is where does one object end; every other colour repeat is deliberate, and a wrap is the one that repeats between neighbours - provably, since a slot is only past the end of the palette once every colour before it was taken by a neighbour, so the fold lands on a colour a neighbour already holds.

    The two messages are compared word for word, in the engine job. That is a stronger pair than the palette or the pixels: a reader who meets this warning in R and then in Python has to be told the same thing, and the pin is what makes comparing prose safe - one exact engine, so a rewording on either side fails here instead of drifting. Measured: of five mutations, changing one phrase of the message is caught by that test and by nothing else.

2026-10-15 - instances come back into R

Added

  • predict() returns the objects. It refused an instance fit until now, and the refusal was right for as long as the bridge had no call that returned a label map. A named list of integer maps, one per image, objects numbered from 1 and 0 for background.

    Named rather than ordered, and that is the part worth stating: the engine’s own list is unnamed, and anything pairing two sequences by position is one dropped batch away from naming the wrong picture - the mistake predict_stream() exists on the semantic side to avoid. The names are read from the same two objects the engine pairs internally, and a test asserts they are the keys evaluate_cases() reports.

    A list rather than an array for the reason the detection one is a list: images differ in size and so does the number of objects.

  • decode = picks which decoding turns the channels into objects, by the name in the model’s decode list. Unset takes the model’s first, which is the engine’s default rather than one restated here - and an unknown name is refused by the engine, naming the ones the model does ask for. Refused outright on a fit that decodes nothing.

  • instance_sizes() is one row per object: voxels, and with spacing either area_mm2 or volume_ml. The question [#103](https://github.com/maju116/rplatypus/issues/103) opens with is how many nuclei, and how big is each one, which the published weights’ card cannot answer.

    The unit is in the column’s name rather than in the documentation, because a column whose unit lives elsewhere ends up in a paper as a bare number. Without spacing there is no such column at all, rather than a count pretending to be a measurement. Millilitres for a volume, as [mask_volume()] reports them, and a test holds the two to the same arithmetic.

  • flow_to_colours() draws a two-channel vector field: hue is the direction, value is the length. A convention rather than a decision - which is why it is not in drawing_style() - and it is what makes a separation_flows() model debuggable, because a field that is right everywhere except reversed looks obviously reversed here and identical in any loss.

    Pixel-identical to the engine’s on random fields, which is the only thing that can hold a convention.

Fixed

  • type = "probability" is refused on an instance fit, by name. An instance model’s channels are not all probabilities: the class channels are and a flow field’s components are raw, because a softmax across a flow component and a class returns a number that means nothing. The engine refuses to conflate the two and so does this - the value is type = "channels", which says what it gives.

  • space is refused on an instance fit, with the reason rather than “unsupported”. Resampling a label map interpolates between object numbers, so object 3 beside object 5 comes back with a rim of object 4. A refusal saying only that it is not supported would read as a gap somebody might fill.

Measured

  • A one-row flow field had no dimensions. field[1, , ] on a 2 x 1 x w array drops to a vector, so the picture came back with no dim at all - and a tiled model hands back exactly that shape at the edge of an image. Found because the comparison against the engine ran three shapes rather than one; with only the first it would have shipped.

2026-10-15 - drawing instances

Added

  • overlay_instances() draws an instance label map over its image, with one colour per object chosen so that no two touching objects share one. The rule is adjacency rather than identity: a colour repeats across the picture and never between neighbours, because nobody reads object 214 by its colour and everybody needs to see where one object ends.

    That is an exact graph colouring - Welsh-Powell, greedy in order of descending degree - and it is affordable rather than clever. Measured in the engine over all 670 Data Science Bowl cases, 524 of which hold touching objects: the hardest needs three of the eight slots in class_colours, while the cheap alternative of colouring by object number modulo the palette paints 550 of 5436 adjacent pairs in one colour, 10.12% - one touching pair in ten drawn as a single object, in a figure whose whole subject is whether two objects are two.

    Eight-connected, so two objects meeting at a corner get different colours. A label-maker goes the other way and joins only along edges, because there the risk is merging two objects into one; here the risk is drawing two as one, which is the opposite direction.

  • overlay_instance_agreement() is found, missed and invented objects. overlay_agreement() answers the same three-way question about pixels, and on an instance result that is the wrong unit: a merged pair and a split object are both nearly perfect pixelwise and both wrong, which is what an average precision will not tell anybody. Matched whole object against whole object at one IoU threshold, strictly greater, and below 0.5 is refused for the reason the metric refuses it.

Measured

  • The matching needs no greedy pass, and that is provable rather than convenient. The engine matches greedily on descending IoU; this package matches every pair above the threshold, which is equivalent above 0.5: if two disjoint true objects both exceeded 0.5 against one prediction, each intersection would exceed half of it - the union is at least the prediction - and two disjoint intersections cannot together exceed it. So the matching is one to one whatever order it is taken in, which is also why the metric refuses a lower threshold.

    Written as the equivalent rather than as a copy because argsort is not stable: two pairs at the same IoU leave the engine in an order neither package controls, and a pixel-for-pixel test would then fail for something that is not a divergence.

Fixed

  • Nothing held the two packages to the same colouring, and the shared constant could not. [#154](https://github.com/maju116/rplatypus/issues/154)’s subject: the palette is mirrored and test-drawing-style.R holds it, so the two would keep agreeing about which eight colours while disagreeing about which object gets which. tests/testthat/test-instance-drawing.R draws the same pictures both ways and compares them pixel for pixel - five label maps including three objects each touching the other two, and five ways an instance result goes wrong - which is the only thing that can hold a rule rather than a constant.

    Six mutations, each caught: four-connected instead of eight, colour by object number instead of by adjacency, ascending instead of descending degree, >= instead of > at the threshold, and two ways of getting the outline wrong. The outline pair needed a new picture: against the first one both mutations passed, because every object in it was three pixels across and had no interior to lose. §4’s “a check calibrated loosely enough admits the failure it was written to prevent”, found by mutating rather than by reading.

  • flow_to_colours() is still deferred, and the stated reason has expired. [#154](https://github.com/maju116/rplatypus/issues/154) defers it because “R cannot configure flows until pyplatypus[#160](https://github.com/maju116/rplatypus/issues/160)” - which shipped in 0.8.0a20, and separation_flows() has been exported here since. The reason that holds now is a different one: predict() refuses an instance fit, so there is no way to get a flow field into R to draw. It belongs with [#103](https://github.com/maju116/rplatypus/issues/103), where the prediction comes back.

And each channel is an independent binary question - a sigmoid per channel rather than one softmax across them - so a voxel may be in several regions at once, which is the point.

The engine reports classes by position, and with regions a position is the one thing a reader cannot resolve: missing_classes: 1 means the second region, and counting entries in a configuration file to find out which is the step nobody takes. With colormap or labels the number is the class, so it stays a number - naming it would invent something the specification did not say, and a test holds that.

    It matters most for the one failure regions invites: of = 3 against a label map holding 4 is a channel of zeros, so the model trains to predict nothing and scores a Dice of 0 for that region while every other number in the run looks ordinary.

    The positions are still attached as the present and missing attributes, so anything reading them keeps working. The mapping is derived in R from the specification R owns rather than asked of the engine - which would mean a release and a pin move for a label - and what holds the two together is a test comparing R’s name against the engine’s own refusal sentence. An off-by-one in that mapping fails it, which is the one mistake whose output otherwise looks entirely ordinary.

  • The exclusivity check is three-way and names what was given. One of colormap, labels and regions, in one message, matching the engine’s own sentence - and the message now says which arguments it found rather than only that one was expected.

  • save_class_masks() writes an overlapping prediction, one file per class. Needs pyplatypus 0.8.0a23, which is what the pin moves to here, and where the writer lives; this side forwards to it rather than keeping a second copy of the rules, because the filenames are part of what somebody’s next script reads. <name><suffix>_<class>.png, black and white, and a class name becomes a filename by replacing anything a path cannot hold with _ - so whole tumour is whole_tumour. Two class names that become the same filename are refused rather than written: one file would hold the second class, the first would be silently gone, and the number of returned paths would still be right.

    The argument is classes and not names, which is §3A applied before the surface existed: names in this family is the files - save_masks() and save_volumes() both use it that way - and a sibling writer where the same word means the classes instead would accept a call copied from one to the other whenever the counts happened to match. The engine’s own function calls them classes too, for the same reason.

Fixed

  • save_masks() and save_volumes() refuse an overlapping prediction instead of silently reducing it. Both took which.max over the channel axis, which for sigmoid channels writes one of the classes a voxel is in and leaves nothing in the file to say so. They now count how many channels are hot at the most ambitious voxel and refuse with that number, each pointing at its own per-class writer.

    [#152](https://github.com/maju116/rplatypus/issues/152) named save_masks() and there turned out to be three reduction sites, not one: save_volumes() has two, a 4-dimensional array inside a list and a 5-dimensional stack. Found by asking what a BraTS user would actually run, which is §4’s a feature is not shipped until something has used it the way a user reaches it applied to a refusal.

    Detected from the array rather than from the specification, which is the same test the engine applies in onehot_to_colours - so both halves refuse the same arrays, and a caller holding only a prediction can answer the question. A softmax prediction never trips it, since its channels sum to one and at most one can reach half; that control is a test rather than a sentence, because without it every ordinary run would start refusing.

  • save_class_volumes() is the same thing for volumes, and it is the case regions was built for. BraTS names three overlapping regions and stores them as volumes, so a writer that only handled pictures would have left the motivating dataset with a refusal and no route to disk. One NIfTI per class, each carrying the geometry of the scan it was predicted from - which is the whole reason this is not save_class_masks() with another extension.

    It needs no engine release: it goes through the same volume writer save_volumes() uses, so the affine, the integer labels and the grid check are those rather than a second copy. What is a second copy is the rule turning a class name into a filename, because the volume path never reaches the engine’s class_filename - so a test holds R’s rule to the engine’s over the names that are actually awkward, rather than a comment claiming they agree.

  • predict(type = "class") refused rather than computed when the classes overlap, and "class" is the default, so this is the first call an R user makes on such a fit. There is no one class per pixel to return: the channels are independent binary questions, they do not compete, and an argmax across them names one of the classes a pixel is in. The refusal says to ask for type = "probability" and names what writes it.

    Read off the specification the fit carries, which is a lever this package owns - the shape cannot answer it, because sigmoid channels and a softmax’s channels are the same array.

  • A single of value would have crossed over as a number rather than a list. reticulate turns a length-1 integer vector into a Python scalar, and the schema wants an array, so of = 4 had to be built with as.list(). Measured both ways before the code was written, and the engine refuses the scalar - so this would have been a refusal nobody could read rather than a silent wrong answer, on the most ordinary region there is.

    Still in [#152](https://github.com/maju116/rplatypus/issues/152), deliberately not here, and written as a paragraph rather than a heading because R CMD check reads every ### in this file as a version and says so: save_masks() refusing an overlapping prediction and the per-class writer that replaces it, inspect_masks() naming regions rather than numbering them, and the guide section. Each is independently worth having, which is why none waits for the others.

[0.2.0] - submitted to CRAN on 2026-10-14

A different package from 0.1.1 under the same name, and the section below says how different.

Migrating from 0.1.1

This was in the README until 2026-10-07 - seventy lines between ## Installing and the first example, about a version the reader does not have, before the one they do. It is here because this file is where R keeps what changed between versions, and because the renames table below was a second copy of one the README already carried; the fuller of the two survived.

Code written against the 2020 release will not run on this one. That version built Keras models through the R keras package and handed them back to you; this one describes a whole run as a specification and computes it in PyTorch. Of the 37 functions and objects the old version exported, 30 are gone — including all of yolo3(), darknet53(), load_darknet_weights(), get_boxes(), non_max_suppression(), plot_boxes(), segmentation_generator() and the annotation readers.

Seven names survive, and three of them are the ones to watch, because they are still exported, still callable, and mean something different:

name 0.1.1 now
u_net() u_net(net_h, net_w, grayscale, ...) → a Keras model u_net(name, input_shape, ...) → one model in a specification
plot_masks() plot_masks(images_paths, masks, labels, colormap) plot_masks(images, prediction, truth, ...)
loss_dice() no arguments, returns a Keras loss loss_dice(smooth = 1), returns a loss to name in a specification

The other four — binary_colormap, voc_colormap, binary_labels, voc_labels — are the same data as before.

Object detection is back, and the names are different. The old package handed you a Keras YOLOv3; this one describes a detector in a specification like everything else. So those five names are gone rather than moved, and what replaces them is:

0.1.1 now
yolo3(), darknet53() yolo3() as one entry in platypus_spec() - same name, a specification rather than a model
load_darknet_weights() weights = "bccd-yolo3", or a path, or hf://owner/repo/file@commit
get_boxes(), non_max_suppression() done inside predict(), which returns boxes already suppressed and in each image’s own pixels
plot_boxes() plot_boxes() - same name, takes what predict() returns

The annotation readers are gone as functions and are now what detection_data() reads for you: Pascal VOC XML or LabelMe JSON, named rather than guessed.

The old release is still there and still installable, pinned:

remotes::install_github("maju116/rplatypus@0.1.1")

Its source is on the master branch, and the issues filed against it stay open. What has aged is its dependencies rather than its code: the pinned TensorFlow no longer installs on a current Python, which is the reason for a rewrite rather than a consequence of one.

  • inspect_masks() and platypus_fit(check_masks = FALSE): a declared class appearing in no mask has a target channel that is zero everywhere, so the model is never shown what it is being asked to find, and platypus_fit() now refuses on it. A threshold on the unmatched fraction cannot do this job - on a 0.6% lesion a wholly wrong colormap is quieter than JPEG artefacts in healthy data.
  • Every help page renders its markdown. DESCRIPTION had no Roxygen: list(markdown = TRUE) although every page had been written in markdown since the rewrite began, so not one cross-reference was a link: 0 to 42 links, 0 to 266 inline code spans, 36 of 40 pages changed. Nothing in the sources was wrong; nothing was converting them.

2026-09-27 - engine 0.3.0a6, then 0.3.0a8

  • predict(space = "source"): map a prediction back out of the model’s grid onto the grid of the scan it came from, undoing the resampling and the crop. Returns a list, and the type change is the API being honest - scans differ in size, and quietly resizing them to match is how a mask ends up describing anatomy it was not computed from.
  • Named weights. weights = "dsbowl-unet" from the registry, hf://owner/repo/file@commit, or a local path, plus export_weights() for your own. A registry name carries a commit and the hf:// form requires one, because weights that change under a stable name are the worst kind of irreproducibility.
  • The Data Science Bowl vignette now opens with a mask in four lines - published weights, fit = FALSE, plot_masks() - before any mention of training. First contact should not need a GPU and an afternoon.
  • Fixed, and found by writing that vignette: weights = "dsbowl-unet" could not work from R at all. The bridge asked for pyplatypus with no extras, so huggingface_hub was never in the environment reticulate builds. Nothing in either test suite could have caught it - the engine’s tests install the extra deliberately and the R tests ran where it was already present.
  • The README says what changed since 0.1.1, written by diffing the two NAMESPACE files rather than from memory: of 0.1.1’s 37 exports, 30 are gone, and three of the seven survivors are worse than gone because they are still callable and mean something else.

2026-09-26 - engine 0.2.0a2 through 0.3.0a5

The day the package stopped being a bridge and became a surface. Five engine releases, each followed here.

  • A worked vignette on the Data Science Bowl, precomputed so that reading it needs no GPU, and a README.
  • Continuous integration: five R CMD check jobs - Ubuntu on R devel, release and oldrel-1, plus macOS and Windows on release - and an engine job that installs the built package and runs the suite against the engine resolved from PyPI. That last one is the job that matters: pkgload::load_all() exposes a package’s internals, library() does not, and local work had been using the most permissive of the three ways a test can reach them.
  • Plotting and masks: plot_masks(), plot_boxes(), overlay_mask(), overlay_agreement(), read_masks(), unite_masks(), mask_coverage().
  • DICOM, properly: modality LUT, a fixed window, MONOCHROME1 inverted. Plus series_report() for a folder of slices, whose decision is that a problem is a column, not an exception - a hundred cases contain a few bad ones, and stopping at the first turns an afternoon into a week.
  • Splitting by patient (split_dataset(), split_path()) and evaluate_cases().
  • Volumes. input_shape = c(64, 64, 32) had been building a 3D U-Net since the first release; what was missing was reading NIfTI, where orientation is the whole problem, and labels as a second way to describe a mask, because volumes label with integers. save_volumes() writes NIfTI carrying the affine of the scan the mask was predicted from - without it a mask cannot be laid over its scan by any viewer, and the file looks perfectly normal while being wrong. mask_volume() reports millilitres, because a voxel count is meaningless outside one scanner.
  • target_spacing: resample to a common voxel size. What makes it necessary is not slice thickness but field of view - forty slices of 1 mm is 40 mm of patient and forty of 2.5 mm is 100 mm, which is the ordinary state of clinical data.
  • channels_from: one channel per file, stating the order and never inferring it. A model trained with FLAIR in channel one and used where channel one is T1 answers plausibly, with the right shape and range, and nothing downstream can tell.
  • Augmentation in 3D, and available_transforms(rank = 3) to say what is usable - 97 of albumentations’ transforms accept a volume and the rest raise from inside the library.
  • A second vignette, on volumes, which generates its own data. It ends on a model at Dice 0.88 whose volumes are 12-23% too large, which is the argument for reporting volume beside overlap: Dice is dominated by an object’s interior and forgiving about its boundary.
  • segmentation_data(window = ) replaced dicom_window, since NIfTI needs the same thing. The old name is still accepted; giving both is an error.

2026-09-25 - engine 0.2.0a1

The package exists.

  • The bridge. py_require() plus uv, resolving an isolated ephemeral environment at library(rplatypus) - deliberately not the shared-Python arrangement that broke this package’s Keras stack in 2020. platypus_status() says what it found rather than leaving a failed import to be guessed at, and PLATYPUS_ENGINE_PATH points the bridge at a source tree during development.
  • platypus_spec(), built either from arguments or from a YAML file and producing the same thing. One pipeline, two constructors.
  • platypus_fit(), evaluate(), predict(), training_history(), and the engine’s complaints translated into R conditions rather than passed through as Python tracebacks.

[0.1.1] - 2020-10-17

The last release of the TensorFlow package, kept here for the record rather than as an ancestor of the entries above. It built Keras models through the R keras package: yolo3() and darknet53() with load_darknet_weights() for the original Darknet weights, a plain u_net(), segmentation_generator(), loss_dice(), the COCO and VOC colormaps, and readers for LabelMe JSON and Pascal VOC XML.

It is still installable and still pinned:

remotes::install_github("maju116/rplatypus@0.1.1")

Its source is on the master branch and the issues filed against it stay open. What has aged is its dependencies rather than its code - the pinned TensorFlow no longer installs on a current Python, which is the reason for a rewrite rather than a consequence of one.
